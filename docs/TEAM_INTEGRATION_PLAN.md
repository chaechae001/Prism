# 개인 PRISM과 팀 filter-bubble 통합 계획

> 아래 초기 관측은 업로드 준비 당시 기록입니다. 사용자가 개인 업로드를 승인했으며 현재 개인 구조는 [저장소 구조](REPOSITORY_STRUCTURE.md)를 따릅니다. 팀 저장소 검토·수정은 아직 수행하지 않았습니다.

## 업로드 전 관측 · 2026-10-22

- 개인 원격: https://github.com/chaechae001/Prism — 공개, 기본 브랜치 이름 main, 아직 브랜치/커밋 없음. 연결된 GitHub 계정의 push 권한 확인.
- 로컬: 기존 폴더는 Git 저장소가 아니어서 main으로 초기화하고 개인 origin만 등록. 아직 커밋/푸시하지 않음.
- 팀 원격: https://github.com/minjun91a/filter-bubble — 현재 연결된 GitHub 앱에서 404, 공개 조회도 404. 사용자가 비공개 레포임을 확인하고 접근 권한 확인 중.
- **팀의 최신 파일·브랜치·DB 구현을 읽지 못했으므로 비교 검토가 끝난 것으로 표시하지 않습니다.** 아래는 권한 확보 후 수행할 통합 절차와 현재 로컬 기준 제안입니다.

## 두 레포의 역할

개인 Prism은 정채은의 UI와 뉴스별 AI 대화를 개발·검증하는 공간으로 사용합니다. 팀 filter-bubble은 최민준의 수집·DB/API와 검토된 프론트를 합치는 공동 기준으로 사용합니다. 개인과 팀은 서로 다른 레포이므로 로컬 브랜치를 만들었다고 팀에 코드가 자동 반영되지 않습니다.

지금은 개인 origin만 등록했습니다. 팀 레포는 승인된 검토/통합 작업을 시작할 때 별도 checkout으로 준비합니다. 개인 원격을 팀 주소로 바꾸거나, 무관한 두 히스토리를 곧바로 병합하지 않습니다.

## 브랜치 제안

아래 이름은 제안이며 원격 브랜치를 아직 생성하지 않았습니다.

| 레포 | 브랜치 | 용도 |
|---|---|---|
| 개인 Prism | main | 현재 검증한 로컬 데모와 설치 방법을 첫 기준으로 저장 |
| 개인 Prism | dev | 다음 작업 통합·검증 |
| 개인 Prism | feat/작업명 | dev에서 분기, dev로 검토·반영 후 main 갱신 |
| 팀 filter-bubble | 기존 기본 브랜치 | 최신 실제 코드 확인 후 이름 유지, 검증한 공동 버전 |
| 팀 filter-bubble | feat/frontend-social-dm | 팀 최신 기본 브랜치에서 생성해 검토한 프론트 변경만 이식 |
| 팀 filter-bubble | feat/rss-body-ingestion | 기존 RSS와 분석가 본문 연결. 팀원이 기존 작업 브랜치를 쓰고 있다면 그 이름 유지 |

개인은 main/dev와 짧은 기능 브랜치로 비교 기준과 진행 중 작업을 나눕니다. 팀 브랜치는 실제 최신 코드를 확인한 뒤 합의합니다. PR 리뷰·테스트 성공 후 기본 브랜치에 합치는 것을 공동 규칙으로 제안합니다.

## 폴더 제안

현재 폴더를 우선 유지합니다. 접근 후 실제 팀 구조와 다른 경우 옮길 이유·대상·실행 경로를 먼저 정리합니다.

```text
frontend/                 정채은: React 화면·브라우저 상태
backend/app/              FastAPI, repository, 공급자 어댑터
backend/tests/            API·데이터 어댑터 검증
contracts/                합의된 API 계약·타입 생성 근거
database/supabase/        검토한 마이그레이션
docs/                     실행·데이터 계약·작업 로그
scripts/                  검증·샘플 생성
```

현재 여러 실행 진입점이 있는 것은 개발 단계별 분리 이력입니다. 이번 개인 버전의 활성 진입점은 `app.api:app`이고 기존 v1 뉴스 조회를 포함합니다. `main.py`는 Mock, `connection_api.py`는 연결 기반, `news_api.py`/`news/`는 중단된 네이버 v2 실험 기록입니다. 실제 팀 API로 통합할 때에는 팀의 기존 app에 social router를 등록하고 공통 repository를 사용해 실행 진입점을 하나로 모으는 방향을 우선 검토합니다. **팀 파일을 보기 전에 이름만으로 삭제하거나 교체하지 않습니다.**

## 접근 권한 확보 후 확인 순서

1. 기본 브랜치·기능 브랜치·열린 PR·최근 커밋을 읽고 비교 기준 SHA를 기록합니다.
2. 팀의 AGENTS/README/환경 예시/의존성/실행법을 확인합니다. 비밀 키 값은 읽어 출력하지 않습니다.
3. 다음 항목을 같은 표로 비교합니다.

| 항목 | 개인 현재 상태 | 팀에서 확인할 내용 | 적용 방향 |
|---|---|---|---|
| 목록/상세 | 기존 v1 계약 재사용, Mock 검증 | 실제 경로·JSON·ID·시간·페이지네이션 | 팀 구현을 기준으로 호환 어댑터 검토 |
| RSS/본문 | reader 교체 지점만 있음, 전문 미연결 | 실제 RSS 테이블·기사 URL·본문 버전·실패 상태 | 팀 수집 코드 유지, 분석가 본문 매칭 추가 |
| 프론트 | 사진 피드·날짜 스토리·댓글·북마크·DM | 팀의 기존 frontend와 충돌/기능 | 필요한 UI 파일만 이식, 폴더 전체 덮어쓰기 금지 |
| LLM | 엘리스 실호출 성공, 기사별 출처 검증 | 팀 모델/요약 파이프라인/키 관리 | 공급자 어댑터 재사용, 서버 문맥 조회를 실제 repository에 연결 |
| DB | 개인 버전에서 변경 안 함 | 현재 스키마·적용 이력·RLS | 기존 스키마 존중, 합의한 추가 migration만 작성 |
| 댓글/DM 기록 | 브라우저 로컬 저장 | Auth·사용자 ID·서버 저장 유무 | 로그인 도입 시 API·RLS 설계 후 서버 동기화 |
| 배포 | 로컬 개발, DM은 로컬 접근만 허용 | 배포 대상·CORS·인증·환경 변수 | 공개 DM 활성화 전 사용자 인증과 한도 구현 |

4. 재사용 / 어댑터 필요 / 수정 필요 / 보류를 파일 단위로 분류하고 비교 문서를 작성합니다.
5. 팀 최신 기본 브랜치에서 기능 브랜치를 만들고 작은 단위로 이식합니다. 개인 레포의 첫 커밋 전체를 팀에 곧바로 병합하지 않습니다.
6. 실제 기사 1개에서 목록 → 상세 → 본문/원문 → DM → 요약/질의응답을 끝까지 검증합니다. 잘못된 ID·실패 응답·본문 없음도 포함합니다.
7. 정채은·최민준이 변경 파일과 DB 영향을 검토한 뒤 팀 PR로 합칩니다.

## 권한이 필요한 지점

팀 레포를 읽을 수 있도록 `chaechae001` 계정 초대가 수락됐는지, Codex GitHub 연결 앱이 해당 비공개 레포에 접근할 수 있는지 확인합니다. 권한을 얻은 뒤 현재 제안을 실제 코드 비교 결과로 보완합니다. 이 문서 작성은 팀 레포에 파일을 전송하거나 메시지를 보낸 작업이 아닙니다.
