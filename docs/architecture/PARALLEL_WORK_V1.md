# 기다리지 않고 병렬 개발하는 작업 기준 v1

기준일: 2026-10-22. 이번 기준은 이전 RSS 요청서보다 우선합니다. DB에 적용된 스키마를 복제한 명세가 아니라, 관측한 현행 구조에 RSS 수신 계층을 추가하는 개발 기준입니다.

## 핵심 원칙

**본인은 샘플로 화면/API를 개발하고, 팀원은 같은 형식으로 수집/저장을 구현합니다. 실제 데이터 전달을 개발 시작 조건으로 삼지 않습니다.**

ERD만 맞춰도 JSON·날짜·상태·조회 함수가 다르면 다시 기다리게 됩니다. 따라서 테이블 관계와 함께 ‘반환 형식’도 고정합니다.

## 1. 오늘부터 두 사람이 같이 사용할 파일

| 파일 | 사용 방법 |
| --- | --- |
| `NEWS_SERVICE_ERD_V1.md` | 현행 DB와 추가할 테이블 구분, 데이터 사전 |
| `news-service-erd-v1.mmd` | 핵심 ERD 원본 |
| `account-erd-v1.mmd` | 마이페이지 후속 ERD. 지금 전부 구현하지 않음 |
| `rss-record-v1.schema.json` | 내부 RSS 정규화 데이터 반환 형식. 기존 공개 API 변경 아님 |
| `rss-record-v1.examples.json` | 본인이 즉시 읽어 개발할 가상 기록 2개 |
| `fixtures/*.xml` | 팀원이 즉시 파서/저장을 시험할 직접 작성한 XML 4개 |
| 기존 `contracts/openapi.json`와 `contracts/fixtures.json` | 기존 화면용 Story API와 Mock 유지 |

`examples.json`은 RSS 레코드 배열입니다. 실제 언론사의 기사/모델 결과가 아니며 DB seed로 자동 적용한 파일도 아닙니다. 매체 이용 범위 확인을 대신하지 않습니다.

## 2. 담당 파일을 고정합니다

| 영역 | 본인 담당 | 팀원 담당 |
| --- | --- | --- |
| UI | `frontend/` 전체, 모바일/보라색 디자인, 빈 목록·로딩·오류·요약 대기 | 수정하지 않음 |
| FastAPI | `backend/app/main.py`: 기본 요청 지원, CORS, 엔드포인트 연결 | 수집 때문에 이 파일을 동시에 수정하지 않음 |
| 조회/표시 변환 | 기존 `backend/app/news_repository.py` 또는 별도 연결 adapter, RSS→표시용 변환 | 내부 RSS reader의 약속한 반환 형식 제공 |
| RSS | 제공 JSON 샘플로 adapter 개발 | 새 `backend/app/rss/` 아래 파서·수집·저장·reader 구현 |
| DB/SQL | 직접 테이블을 만들거나 변경하지 않음. API에는 Mock reader 사용 가능 | `database/` migration/seed 단독 소유. 기존 테이블 유지, RSS 테이블 추가 |
| 공통 DB 설정 | 읽어서 사용 | `backend/app/db.py` 설정 담당. 변경 시 변수 이름·필요한 조치만 인계 |
| 테스트 | API/화면/기존 계약 테스트 | XML 파서/재수집 중복/DB 적재·reader 테스트 |
| 공통 형식 | 기존 Story API와 새 내부 RSS v1을 사용 | 같은 형식 사용. 필요한 추가 정보는 기존 키를 깨지 않는 내부 컬럼으로 추가 |

이 분담은 **코드 소유권**입니다. 두 사람이 공유 개발 DB의 같은 테이블에 동시에 DDL을 실행하지 않습니다. schema migration 실행자는 팀원 한 명으로 둡니다.

## 3. 기다림을 없애는 내부 연결 지점

팀원이 구현할 reader의 권장 사용 방식은 다음과 같습니다. 아직 구현된 함수라는 뜻은 아닙니다.

```python
# backend/app/rss/reader.py — 팀원 구현
list_rss_records(limit: int = 10) -> list[dict]
get_rss_record(record_id: str) -> dict | None
```

반환 dict 하나가 `rss-record-v1.schema.json`을 만족하도록 합니다. DB 컬럼과 동일할 필요는 없으며, JOIN/변환으로 publisher_name 등 필요한 값을 구성할 수 있습니다. 저장 실패/서버 오류는 정상적인 빈 배열로 숨기지 않습니다.

본인은 같은 시그니처의 **샘플 reader**를 본인 adapter/테스트 영역에 두고 `rss-record-v1.examples.json`을 읽습니다. 팀원 폴더에 가짜 구현을 넣어 충돌시키지 않습니다. 통합할 때 reader 구현만 DB reader로 교체합니다.

raw 입력에서 필수 제목/URL이 유효하지 않은 행은 parse error로 남깁니다. 위 reader는 표시 가능한 parsed/partial 레코드만 반환하는 내부 계약입니다. 권한 unknown인 레코드를 reader가 읽을 수 있다는 사실이 공개 게시 허용을 뜻하지 않습니다.

이 내부 함수는 HTTP API 엔드포인트가 아닙니다. 공개 API 경로·필드를 추가했다고 취급하지 않습니다.

## 4. 각자 바로 시작할 작업

### 본인: 실제 RSS를 기다리지 않고 진행

1. 기존 MSW의 Story 데이터를 유지하며 모바일 UI와 상태별 화면을 개발합니다.
2. 내부 RSS 샘플 2개를 읽는 adapter/테스트를 만듭니다. 본문/설명 없음, 날짜 미확인, 권한 미확인 상태를 다룹니다.
3. 기존 기본 쿼리 요청과 FastAPI CORS를 맞춥니다. 새 커밋의 오류 응답 처리를 덮어쓰지 않습니다.
4. RSS 원문 미리보기와 정제된 사건 카드를 혼동하지 않게 표시합니다. 원문 제목을 AI 중립 제목이나 description을 AI 요약으로 부르지 않습니다.
5. 미리보기에 기존 Story 형식을 활용한다면 날짜 등 필수 필드가 있는 기록에 한해 임시 1기사 단위로 변환하고, pending/빈 관점·단일 출처임을 명시합니다. 날짜 없는 내부 레코드를 억지로 기존 Article에 끼워 넣지 않습니다. 필요하면 비공개 개발 미리보기 모델에서 ‘날짜 미확인’으로 처리합니다.
6. 날짜 필터/임시 미리보기 ID/북마크의 한계를 구분하고, 실제 군집 결과가 온 것처럼 저장하지 않습니다.

### 팀원: 본인의 UI 완성을 기다리지 않고 진행

1. Supabase의 기존 테이블을 유지하며 private.rss_feeds/private.rss_items 추가 migration을 작성합니다.
2. 제공 XML 4개로 namespace·누락 필드·날짜 오류·미디어 속성 처리를 구현합니다. 수집기와 파서를 분리해 네트워크 없이도 테스트합니다.
3. 같은 XML 두 번 처리 및 다른 피드의 같은 URL 처리로 중복 방지를 검증합니다.
4. DB reader가 샘플과 동일한 키·타입·상태로 반환하는지 검증합니다.
5. 범위가 확인된 실제 소스 하나로 5~10개 수집/적재를 수동 실행합니다. 결과를 기록하되 자격 증명은 코드나 로그에 넣지 않습니다.
6. 본문 분석·군집·LLM·사용자 테이블 확장은 이번 수집 경로 완성의 선행 조건으로 삼지 않습니다.

## 5. 합류 시점은 ‘개발 시작 전’이 아닌 마지막 교체 시점입니다

| 체크포인트 | 본인 결과물 | 팀원 결과물 | 함께 확인할 것 |
| --- | --- | --- | --- |
| 독립 개발 | Mock 카드·상세, API/CORS, 샘플 reader adapter | migration, 파서/수집기, DB reader | 각자 테스트가 통과하는지 |
| 첫 통합 | 샘플 reader를 DB reader로 연결 | 실행 명령·적용 migration·테스트 결과 | 같은 record_id/URL의 데이터가 화면까지 이어지는지 |
| 실제 데이터 | 실제 HTTP 모드로 브라우저 확인 | 합의한 RSS 5~10개, 재수집 결과 | 중복·본문 없음·날짜·출처·원문 링크 |
| 이후 확장 | 사건 카드/요약 상태 연결 | 군집/요약 입력과 결과 저장 | 동일 사건 검증·근거 인용·게시 정책 |

실제 수집 결과가 늦어지면 본인은 샘플로 계속 개발합니다. UI가 늦어지면 팀원은 reader/SQL 테스트로 완료 여부를 확인합니다. 한쪽이 다른 쪽의 완료 화면을 기다리지 않습니다.

## 6. 변경과 Git 규칙

- 별도 작업 브랜치에서 각자 담당 폴더만 커밋합니다. 브랜치 이름 예: `feat/web-api-integration`, `feat/rss-ingestion`. 실제 브랜치를 이번 문서 작업으로 생성하지 않았습니다.
- 한쪽이 공개 응답 키·내부 RSS v1 필드의 의미/타입을 임의로 바꾸지 않습니다. 변경이 필요하면 이유와 전후 JSON을 남기고 기존 샘플도 같이 갱신합니다.
- 변경 기록에는 추가/수정 경로, 실행 명령, 검증 결과, 미완료 항목을 적습니다. 두 사람이 같은 로그를 덮어쓰지 않습니다.
- 기존 요청서에 나온 옛 커밋/담당 분담은 최신 코드 상태로 업데이트합니다. 현재 브랜치에는 오류 처리 개선이 이미 들어 있으므로 같은 기능을 중복 구현하지 않습니다.

## 7. 팀원에게 전달할 메시지 — 존댓말

> 서로 기다리지 않고 진행할 수 있도록 첨부 ERD와 내부 RSS JSON v1을 기준으로 병렬 개발하려고 합니다. 저는 프론트·기본 API 요청·CORS·화면용 변환을 담당하겠습니다. RSS 파서·수집·중복 방지·저장·DB migration과 RSS reader를 담당해 주시기 바랍니다.
>
> Supabase의 기존 public 7개/private 3개 테이블은 유지하시고, 우선 private.rss_feeds/private.rss_items를 추가하는 방향으로 진행 부탁드립니다. 제공한 가상 XML로 먼저 테스트하시고, reader가 제공 JSON 스키마와 같은 형식을 반환하도록 부탁드립니다. 저는 같은 JSON 샘플로 개발하므로 실제 수집 완료까지 기다리지 않겠습니다.
>
> main.py와 화면용 adapter는 제가 수정하겠습니다. DB 변경은 한 분만 적용하도록 담당해 주시고, 필요한 공통 설정 변경은 파일과 조치 사항을 기록해 주세요. 완료하시면 커밋·추가/수정 파일·migration 순서·실행 명령·테스트 결과를 전달해 주시기 바랍니다. 이후 reader를 연결하여 실제 RSS 데이터로 함께 확인하겠습니다.

## 지금 완료를 주장하지 않는 것

이 파일들은 설계와 작업 기준입니다. 새 RSS 테이블/reader/adapter/보라색 UI를 실제로 구현하거나 DB에 적용한 결과가 아닙니다. 이번 목표는 두 사람이 같은 기준과 즉시 쓸 샘플을 가지고 독립적으로 개발을 시작할 수 있게 만드는 것입니다.
