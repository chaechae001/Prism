# 군집 요약·품질 평가·계정 저장

현재 실행은 비회원 모드입니다. 로그인·회원가입·인증 메일은 후속 개발로 보류했습니다. 아래 계정 API·검증 절차는 추후 재개용이며 현재 사용자 화면에는 인증 폼을 표시하지 않습니다. 북마크·개인 댓글·DM은 브라우저 저장소를 사용하며 다른 기기와 자동 동기화되지 않습니다.

## 실행

기존 DB·Elice 설정과 활성 군집 배치를 사용합니다. 기본 비회원 실행에는 Supabase Auth 공개 설정이 필요하지 않습니다. 추후 계정 개발 재개 시 `-EnableAccounts`와 루트 `.env`의 `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`가 필요합니다. publishable 또는 anon 공개 키를 사용하고 service_role/secret 키는 사용하지 않습니다.

새 환경에 한해 추가 스키마를 설치합니다. 먼저 기존 이름과 충돌하지 않는지 확인하고, 기존 기사·군집 테이블은 변경하지 않습니다.

```powershell
python -c "from backend.app.services.reader_schema import status; print(status())"
python -c "from backend.app.services.reader_schema import install; print(install())"
```

설치 파일: `database/migrations/20261024_001_summary_quality_accounts.sql`. 비공개 테이블 6개, RLS와 직접 접근 권한 차단을 추가합니다. 이미 설치된 경우 재생성하지 않습니다.

```powershell
./scripts/run-connected-news.ps1 -Python .venv/Scripts/python.exe
# 별도 터미널
cd frontend
$env:VITE_API_BASE_URL='http://127.0.0.1:8006'
npm.cmd run dev:http -- --port 5186
```

화면: `http://127.0.0.1:5186/`. 로그인·쿠키 검증은 localhost와 127.0.0.1을 섞지 않고 같은 호스트를 사용합니다. 실행 스크립트는 테이블을 자동 생성하거나 뉴스를 수집하지 않습니다.

## 요약 생성과 게시 확인

1. 로컬 화면의 **연결 및 피드 설정 → 요약·군집 품질 검토 열기**에서 뉴스를 선택합니다. 일반 이용자의 내 정보 화면에는 표시하지 않습니다.
2. **선택 뉴스 요약 생성**을 누릅니다. Elice API를 호출해 초안을 저장합니다. 같은 입력·모델·프롬프트 버전은 재사용합니다.
3. 초안의 제목·핵심 문장·미확인 사항을 관련 원문과 비교합니다.
4. **승인·홈에 게시**를 누릅니다. 홈과 상세에 사실 중심 제목·AI 요약·인용 출처가 표시됩니다.
5. **게시 보류**를 누르면 대표기사 표시로 돌아갑니다. 기사·권한·배치가 바뀐 초안은 게시하지 않습니다.

전체 본문 확보와 수집·저장·요약·요약 게시 허용 상태를 확인합니다. 현재 전체 24,000자, 기사당 12,000자 입력 범위를 넘겨 발췌가 필요한 군집은 생성하지 않습니다. 큰 군집용 분할 요약은 후속 확장입니다. 엘리스 비스트리밍 프록시 한도에 맞춰 출력 예산은 1,800토큰입니다.

편집 API는 기본 비활성이고 `PRISM_EDITORIAL_ENABLED=1`인 루프백 접속에서만 열립니다. 연결 실행 스크립트가 로컬에서 활성화합니다. 외부 서비스 운영용 관리자 인증 화면은 별도 구현이 필요합니다.

## 군집 품질 확인

같은 도구의 **군집 품질 평가**에서 다음을 확인합니다.

- 기사·군집·단독 군집 수와 언론사 분포
- 사람이 작성해야 하는 기사 쌍 정답과 작성률
- 파일 다운로드·불러오기, 화면에서 같은 사건/다른 사건 표시
- 작성된 정답에 대한 Precision·Recall·F1

예측값은 평가 파일에 포함되지만 정답을 자동 생성하지 않습니다. 사람이 작성하지 않은 상태는 점수를 계산하지 않습니다. 파일의 기사 ID·중복 쌍·데이터 해시가 현재 배치와 맞지 않으면 평가를 거절합니다. 파일 불러오기를 완료하면 서버 검증을 거칩니다. 화면 작성 중 값은 브라우저 새로고침 시 사라지므로 **파일 다운로드로 보관**합니다.

분석가에게 필요한 자료는 서로 다른 언론사의 같은 기간 기사, 동일 사건 판정 기준, 사람이 표시한 기사 쌍 정답, 경계 사례 판단 근거입니다. 성능을 조정하는 개발셋과 최종 평가셋을 분리해야 합니다.

## 회원가입과 기기 간 저장 확인

1. **내 정보 → 처음이라면 회원가입**에 실제 수신 가능한 이메일과 비밀번호를 입력합니다.
2. Supabase의 이메일 확인 설정이 켜져 있으면 인증 메일 링크를 누릅니다. 메일 발송 제한·SMTP 설정은 프로젝트 설정을 따릅니다.
3. PRISM으로 돌아와 로그인합니다. 인증 링크가 다른 기본 주소로 열리면 Supabase Authentication의 URL Configuration에서 사이트 주소와 허용 리디렉션 주소를 개발/배포 주소에 맞춰 설정합니다.
4. 홈에서 북마크, 개인 댓글, 뉴스 DM을 사용합니다. 로그인 상태의 기록은 계정에 저장됩니다.
5. 로그아웃 후 같은 계정으로 재로그인하면 기록이 복원됩니다. 다른 계정에는 이 기록이 보이지 않아야 합니다.
6. 다른 기기에서는 같은 서버에 접근할 수 있는 HTTPS 주소로 접속해 확인합니다. 현재 127.0.0.1 개발 주소는 이 PC 전용입니다.

로그인 전 기록은 기존 브라우저에 남습니다. 계정으로 자동 이전하지 않습니다. 개인 댓글은 다른 사용자에게 공개하지 않습니다. DM 기록은 계정에 저장하지만 저장된 과거 대화를 LLM에 자동 전송하지 않습니다. 따라서 이전 질문의 대명사만 이용한 후속 질문보다 현재 질문에 필요한 내용을 함께 적는 것이 적합합니다.

계정당 DM은 시간당 30회로 제한합니다. 네트워크·모델 실패도 이미 시작된 호출 한도에 포함될 수 있습니다. 로그인 정보 오류는 세션을 발급하지 않습니다. 토큰은 HttpOnly 쿠키에만 있고 클라이언트 응답 JSON에는 없습니다.

## API와 호환성

기존 `/api/v1/stories`와 상세 응답 필드는 유지합니다. 승인된 군집 요약을 기존 `title`, `dek`, `summary` 필드에 연결합니다. 원문 기사 제목·URL·ID는 유지합니다. 요약 게시 상태 변경은 목록 버전에 반영하므로 오래된 페이지 커서는 새로 조회해야 합니다.

추가 API:

| API | 기능 |
|---|---|
| GET `/api/account/session` | 인증 연결 상태·현재 사용자 |
| POST `/api/account/signup`, `/login`, `/refresh`, `/logout` | 인증과 쿠키 관리 |
| GET `/api/account/workspace` | 내 북마크·개인 댓글·DM 기록 |
| PUT/DELETE `/api/account/bookmarks/{story_id}` | 내 북마크 저장·해제 |
| POST `/api/account/comments` | 개인 댓글 저장 |
| DELETE `/api/account/comments/{comment_id}` | 내가 작성한 댓글 삭제 |
| POST `/api/account/threads/{story_id}` | 뉴스 DM 방 생성 |
| POST `/api/social/stories/{story_id}/chat` | 기존 응답 유지, 로그인 시 검증된 질의·답변을 서버 저장 |
| GET `/api/editorial/candidates`, `/drafts` | 로컬 편집 후보·초안 |
| POST `/api/editorial/stories/{story_id}/generate` | 군집 요약 초안 생성 |
| POST `/api/editorial/drafts/{id}/review` | 명시적 승인·보류 |
| GET `/api/editorial/quality` | 품질 현황과 정답 작성 양식 |
| POST `/api/editorial/quality/evaluate` | 사람이 작성한 정답 평가 |

추가 계약은 `contracts/workspace-openapi.json`, 생성 타입은 `frontend/src/api/workspace-schema.d.ts`입니다. 뉴스 v1 계약과 기존 생성 타입은 변경하지 않습니다.

## 로컬 기사 본문과 인증 메일

로컬 연결 실행에서는 `PRISM_BODY_PREVIEW_ENABLED=1`로 대표기사 본문을 별도 `/api/local/stories/{id}/body`에서 최대 6,000자 읽습니다. 게시물의 더 보기로 펼치고, 초과분은 발췌로 표시합니다. 기본은 비활성이며 외부 클라이언트에는 제공하지 않습니다. 기존 뉴스 목록 JSON에는 본문을 넣지 않습니다. 외부 배포의 본문 표시 허가와 접근 정책은 별도 확인이 필요합니다.

인증 메일 다시 요청은 `/api/account/resend`를 사용합니다. API 수락은 이메일 수신함 도착을 보장하지 않으며, 이미 인증한 계정은 로그인해야 합니다. 발송 한도·허용 주소·메일 서버 오류는 구분해 표시합니다.

Supabase 기본 메일 서버는 프로젝트 팀 주소와 제한된 발송량을 대상으로 합니다. 일반 사용자 가입을 운영하려면 [공식 SMTP 안내](https://supabase.com/docs/guides/auth/auth-smtp)에 따라 사용자 지정 SMTP를 설정합니다. 오류가 확인되면 Authentication의 메일·SMTP·Auth 로그 설정을 점검합니다. 인증을 건너뛰도록 사용자를 강제 승인하지 않습니다.

## 배포 전 남은 검증 항목

- 실제 계정 회원가입·이메일 인증·재로그인 및 다른 기기 복원
- 여러 언론사 입력과 사람 정답 기반 군집 평가
- 요약 사실성·중립적 표현에 대한 검토 기준과 평가 자료
- HTTPS 보안 쿠키, 리디렉션, 허용 Origin, 관리자 인증·운영 관측

기능 단위·DB 통합 테스트 통과는 위 실사용 검토를 대체하지 않습니다.
