# 현재 단계 점검과 업무 분담

작성일: 2026-10-22. 검토 저장소: https://github.com/minjun91a/filter-bubble

검토 브랜치: `feat/backend-api`, 커밋 `22cd6e8437ea5fe503df67667fc460fcce941567`.
같은 시점의 `main`은 `4ccf1bff5e2240098ef5fcb27f78dfb3a68da074`로, 백엔드 작업 브랜치와 다르다. 이번 점검에서 병합·푸시·DB 적용은 하지 않았다.

## 현재 판단

**현재는 ‘수동 입력 가상 데이터의 DB 조회 구현 → 프론트 통합 검증 직전’이다. RSS 수집 단계가 완료된 상태가 아니다.**

팀원은 처음 전달받은 범위에 맞춰 조회 코드를 구현했다. RSS 입력 구조의 보완은 이번에 추가로 공유해야 할 다음 요구사항이다. 기존 작업을 폐기하거나 모든 API를 RSS 모양으로 바꿀 필요는 없다.

팀원 문서에는 공용 개발 DB 저장과 수동 테스트 성공이 기록되어 있다. 이번 점검에서는 실제 DB에 접속하지 않았으므로 이를 독립적으로 재검증했다고 표시하지 않는다. `/health` 200도 현재 코드에서는 DB 연결 확인이 아니다.

## 지금 수정할 항목

### 1. 첫 화면 요청이 422 — 연결을 막는 항목

팀원 [main.py L62–](https://github.com/minjun91a/filter-bubble/blob/22cd6e8437ea5fe503df67667fc460fcce941567/backend/app/main.py#L62)는 모든 쿼리 파라미터를 거부한다. 현재 프론트는 첫 요청부터 `q=&mode=balanced&diversity=70&limit=6`을 보낸다. 사건이 한 건이어도 기존 기본 요청은 지원해야 한다. 단순 JSON 필드 모양을 맞추는 것만으로는 호출 계약이 맞지 않는다.

### 2. CORS 미설정 — 브라우저 연결을 막는 항목

현재 앱에 CORS 미들웨어가 없고 개발 origin/X-Mock-Scenario 헤더의 preflight가 405를 반환했다. 프론트와 API를 다른 origin에서 연결할 때 해결해야 한다. [FastAPI 공식 설명](https://fastapi.tiangolo.com/tutorial/cors/)을 참고한다.

### 3. 카테고리/피드백 API와 오류 응답

카테고리·피드백 경로는 404다. 카테고리는 계약에 맞게 구현하고, 피드백은 구현 시점·개발용 응답·화면 비활성화 여부를 합의한다. DB 실패를 모의하면 500 text/plain이며 요청 ID 헤더가 없다. 공통 JSON 오류를 추가해야 프론트가 안정적으로 오류를 안내할 수 있다.

### 4. 계약 전달 자료 누락

팀원 `docs/API_CONTRACT.md`가 가리키는 OpenAPI·examples·models 일부가 해당 브랜치에는 없다. 전달 패키지의 명세와 실제 서버 명세/응답을 대조할 필요가 있다.

### 5. RSS 입력 구조 — 다음 단계 보완

현재 `stories/articles`는 화면에 표시할 사건·기사용이다. `raw_text`와 분석용 text를 필수로 받는 영역만으로는 제목/URL만 오는 RSS를 수신하기 어렵다. feed 등록부, nullable 콘텐츠, 원본 날짜·파싱 상태, 안정 ID, 유입 관계, 단계별 이용 확인 상태를 비공개 수신 계층에 추가한다. 상세 항목은 요청서에 있다.

후속으로 공개 기사 제외/철회 시 요약의 인용 기사 ID가 여전히 유효한지도 검사해야 한다. 실제 데이터를 게시하기 전 검증 항목이며, 현재 가상 3개가 모두 공개된 예제의 실패를 뜻하지는 않는다.

## 지금 본인이 할 일

1. **보완 요청서와 전달 ZIP을 팀원에게 보내기.** 저장소 링크만 보내면 로컬에만 있는 RSS 점검 자료는 전달되지 않는다. 이번 작업은 전송/메시지를 대신 보내지 않았다.
2. **역할 고정:** 본인은 프론트/화면 테스트, 팀원은 DB/API/수신 모델. 같은 파일을 동시에 수정하지 않기.
3. **UI는 Mock으로 병렬 개발:** 모바일 타임라인·보라색 테마, 로딩/빈 목록/오류, 요약 상태별 화면. API 응답 필드를 UI 때문에 변경하지 않기.
4. **팀원의 A 완료 후 실제 HTTP 연결 확인:** MSW와 실제 서버를 동시에 성공 근거로 혼동하지 말고 `VITE_API_MODE=http`로 재시작해 확인. API base URL도 확인.
5. **RSS 설계안 검토:** 전문 SQL을 혼자 판단하기보다 ‘본문 없는 항목을 저장할 수 있는가, 중복 방지가 되는가, 기존 API가 유지되는가’의 예시·테스트 결과를 요구하기.
6. **DB 반영 후 회귀 확인:** 기존 가상 사건 1개·기사 3개가 계속 화면에 표시되는지 확인. 날짜 필터는 현재 로드한 사건의 `updated_at` 기준이므로, 오늘과 seed 날짜가 다르면 전체 날짜/해당 날짜로 검사. 테스트를 위해 발행일을 오늘로 바꾸지 않기.

## 팀원에게 먼저 보낼 짧은 메시지

> RSS 점검 자료를 아직 전달하지 못했어. 기존 가상 사건 1개·기사 3개 DB 조회 작업은 유지하고, 첨부 요청서를 A(API 연결 마무리)와 B(RSS 내부 입력 구조 보완) 순서로 진행해줘. 현재 프론트의 기본 쿼리 요청과 CORS부터 맞추고, RSS용 nullable 콘텐츠·날짜·식별자·피드 관계를 제안해줘. 공개 Story 응답은 유지하고 DB 적용 전 변경표·migration·정규화 JSON을 공유해줘. 나는 그동안 Mock 기반 모바일 UI와 상태별 화면을 작업할게. 실제 수집/AI는 이 두 단계를 확인한 다음에 붙이자.

## 검증 근거와 재현

- `scripts/reviews/check_backend_snapshot.py`는 검토 사본의 DB repository를 메모리 fixture로 대체한다. DB 비밀번호·네트워크 DB 접속·SQL 변경은 사용하지 않는다.
- 결과: `docs/reviews/2026-10-22-backend-route-checks.json`. 목록/상세/누락/기본 쿼리/카테고리/피드백/preflight/DB 예외의 8개 관측이다. ‘실제 DB 통합 테스트 8개 통과’라는 의미가 아니다.
- 실행 환경 FastAPI 0.141.1 / httpx 0.28.1. 팀원의 미고정 requirements를 새로 설치한 환경 재현 검사는 아니다. TestClient에서 httpx 관련 deprecation 경고가 있었으며 제품 코드 실패와 구분한다.
- 최초 제한 환경 검사는 종료되지 않아 중단하고 해당 검증 프로세스를 정리한 뒤, 별도 실행 환경에서 같은 메모리 검증을 완료했다.
- 저장소·브랜치·공개 조건을 읽기만 했으며 실제 개발 DB 상태, SQL migration 성공, RSS 파서/실제 수집, 운영 보안은 검증하지 않았다.
- 이 우선 점검 중 UI/백엔드/DB/공유 계약 코드는 변경하지 않았다. 앞서 요청한 보라색 모바일 UI 복원은 후속 작업으로 남아 있다.
